# SPEC：后台上游推送与「取消」的一致性（S-B5）

- 作者：architect ｜ 日期：2026-10-02 ｜ 状态：**实现已收（`cb83a15`，评审通过）+ 残留缺口已裁决（§8，待 coder 落地）**
- 关联：`docs/SPEC-LOCAL-FIRST-SUBSCRIBE.md`（S-B2 本地优先）、`docs/ARCHITECTURE-REVIEW-2026-10-01.md`
- 归属链：本 spec 是 S-B2 的**收尾条款**——S-B2 把上游推送挪到请求返回之后，就必须补上「推送前重查本地行」这一步，否则取消会漏到上游

## 0. 问题（实证，2026-10-02 00:10）

生产日志（`backend/logs/unisub.log`，同一台机、同一次冒烟）：

| 时刻 | 事件 |
|---|---|
| 00:10:17.665 | `订阅了 盗梦空间 (movie)`（tmdb_id=27205） |
| 00:10:17.772 | `取消订阅 盗梦空间`（**+107ms**） |
| 00:10:17 | `NextFind 订阅成功: 盗梦空间 (movie, tmdb_id=27205)`（后台任务在飞） |
| 00:10:32.740 | `MP 镜像 — 创建订阅: 盗梦空间 电影 (mp_sub_id=2263)`（**取消后 +15s**） |

`activity_logs` 三条时间戳吻合；库内 `subscriptions`/`mp_subscription` 均 **0 行**（父行删除已连带）。
→ **MP 侧留下了 unisub 无记录、无本地镜像的「僵尸订阅」（mp_sub_id=2263）**。NF 侧同理，只是这次时序恰好赶在取消前完成。

根因：`schedule_upstream` 的任务在请求返回后独立跑，**不感知该行是否已被取消/删除**。

## 1. 组件边界

- 「取消」是**本地事实**（行不在了）；后台推送任务必须在**每个上游调用之前重查本地行是否存在**。
- 行不存在 → 放弃该步并写**可见**日志（不静默），不得再调 NF/MP 建订阅。
- 判定状态一律读库，**不许用内存标记**（进程重启即丢，且多 worker 不共享）。
- **（2026-10-02 评审补）事务边界属于契约**：上游**出网调用期间不得持有本地业务行的写锁**。
  守卫读到的必须是「此刻的库」，而不是「上一个事务快照的库」——否则守卫在，证据迟到 12s，等于没有。

## 2. 接口契约

- `schedule_upstream(...)` 产生的后台任务：每步（NF 建订阅 / MP 镜像之前）执行
  `select(Subscription).where(Subscription.id == sub_id)`；返回 `None` → `return`（放弃后续上游动作）。
- 跳过时落一条可见记录：`activity_logs` `action="system"`，message 含「订阅已取消，跳过上游推送」+ 标题。
- 触发频率不变（仍是 commit 之后的独立会话任务）；失败/跳过都不回滚本地、不影响请求返回值。

## 3. 数据格式

- **不变**：不加表、不加列、不加墓碑字段。存在性检查用主键查询即可覆盖本期场景。

## 4. 量级约束

- 每后台任务增加 2~4 次本地查询（<1ms），**不增加出网调用**（补偿路径仅在真竞态时多发 1 次撤单）。
- 订阅请求路径 p95 仍 **< 500ms**（本改动不碰请求路径）。
- **取消路径 p95 < 1s**（不再被后台任务的行锁阻塞；见 §8-A）。

## 5. 非目标（本卡明确不做）

- **不做**「取消时主动撤销上游已建的订阅」（那是 `unsubscribe` 的语义，本期仍同步等 NF，且要处理 MP 侧删除 → 单独卡）。
  **例外（2026-10-02 裁决补）**：后台任务**自己出网窗口内建出来的那一条**上游订阅，若返回时发现本地行已没了，必须撤销
  （精确到本任务刚拿到的 id，有界、幂等）。不得借此扩成全量上游对账。
- 不引入墓碑表 / 状态机 / 消息队列；不做推送去重、不做顺序保证。
- 不改 NF/MP 客户端、不改 http_client、不改 `orchestrator.subscribe` 的返回契约。

## 6. 验收

1. **回归测试（桩，必须真 RED 过）**：订阅 → 立即 DELETE → 手动触发后台任务 →
   断言 NF/MP 的「建订阅」桩调用次数 **= 0**，且活动日志出现「跳过上游推送」。
   没有这条测试不算完成。
2. **真机复验**：订阅一部 → 100ms 内取消 → 30s 后 MP 订阅日志**不得**出现该条目的「创建订阅」（或经 MP API 列表确认不存在）。
   **2026-10-02 评审加严（两条必须同时成立）**：① 取消请求自身的 DELETE 延迟 **< 1s**（不许被后台任务的未提交事务行锁阻塞）；
   ② 30s 后 MP/NF 列表均无该条目 —— 即便出网窗口内真的建了，也必须已被撤销（不是「只记日志」）。
3. `cd backend && unset UNISUB_DATABASE_URL && .venv/bin/python -m pytest -q` 全绿（基线 **209**）。
4. `sudo supervisorctl restart unisub:unisub_backend` → `sleep 3` → `/health` = healthy。
5. **顺带清理**：删掉本次遗留的 MP 僵尸订阅 `mp_sub_id=2263`（用项目已有 MP 客户端；不许打印 token / 不落明文）。
   ⚠️ architect 复核时用 `platform_configs.api_key` 直查 MP 列表得到 **403**（该 key 对该端点无效）→ 该条**未被证实清除**，
   必须用项目内既有 MP 客户端复核（见 §8 卡）。
6. **新增（§8-A/B 落地后）**：真机取消后，后台任务日志应出现「上游窗口内已取消 → 撤销刚建订阅」类记录，且 NF/MP 两侧均无残留。

## 7. 红线

- 只查错不重写：不改动 S-B2/S-B3 已定契约（本地先落库 + commit 后返回 + 幂等）。
- 不许用「取消时删 MP」之类的越权动作掩盖问题；僵尸清理仅限上面那一条 id。
- 不许伪造通过：桩调用计数必须是测试真实断言出来的。

## 8. 修复路线裁决（architect，2026-10-02 评审）

### 8.1 评审事实（`cb83a15` 实测，非推断）

| 项 | 结果 | 证据 |

| 守卫位置 | 通过 | `orchestrator.py` L136（NF 前）、L147（MP 镜像前） |
| 判定只读库 / 不用内存标记 | 通过 | `_local_subscription_exists` + `no_autoflush` |

| 回归测试真 RED | 通过 | pre-fix `695bbab` + 新测试 = `2 failed`，报 `UPDATE subscriptions ... 0 were matched`（StaleDataError） |

### 8.2 洞在哪（代码行级）

`_sync_upstream_inner` **全程只有一个事务**，唯一 `commit()` 在 L191。L152-155 的 `nf_subscribed` 写回在 L179
`begin_nested()` 处触发 flush → 从那一刻起 `subscriptions` 该行持有**排他行锁**，一直持有到 L191；
而 L177-189 的 MP 镜像（实测 **12~15s** 出网）正落在这段锁窗内。后果：

1. 用户的 `DELETE` 被行锁阻塞 ~12s，**取消无法先落库**；
2. 守卫 L147 读到的是**锁窗前**的快照（行还在）→ 照旧调 MP → 上游僵尸。

即：**守卫写对了，事务边界把守卫的证据推迟了 12s**。这是设计缺陷，不是实现书写错误。

### 8.3 裁决：A + B（都做，缺一不可）

- **A 缩短锁窗**：NF 写回后**立即 commit**（NF 已成功，写回安全，避免 L179 才 flush），再执行 MP 前的存在性重查
  （新事务 → READ COMMITTED 能看到刚提交的 DELETE），随后 MP 镜像与其写入尽快 commit。
  镜像是 `MpSyncEngine` 内部实现，若其把出网调用放在写事务里，需一并把出网点移出事务（同一条判据）。
- **B 返回后补偿**：NF/MP 调用**返回后**再查一次本地行；行已不存在 → **撤掉本任务刚建的那一条**上游订阅
  （NF/MP 各一次 remove），落可见日志。只记日志不算修好（上游残留=僵尸，会继续下载）。
- 保留现有两处守卫（它们是快速路径）；A 是让守卫看得见取消，B 是兜住已经漏出去的。

### 8.4 为什么不是别的选项

- 「只调阈值/只加延迟」＝拿时间掩盖竞态，量级一涨就复发。
- 「取消异步化」＝把竞态从后台挪到队列，不解决「出网窗口内本地事实不可见」，且新增组件（违反 §5 非目标）。
- 「取消时全量对账上游」＝越权 + 放大出网调用（违反 §5）。
